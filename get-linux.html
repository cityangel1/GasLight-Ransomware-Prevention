Get GasLight for Linux

Clone, build, and run — a script automates all three. This is also where current development effort is focused: real PID-attributed file writes via fanotify, persistence monitoring, and network monitoring, all entirely from user space.

1

Clone the repository

# clone the real repo:
git clone https://github.com/cityangel1/GasLight-Ransomware-Prevention.git
cd GasLight-Ransomware-Prevention
2

Run the install script

Checks for a Rust toolchain (installs one via rustup if missing), builds a release binary, and runs the test suite — safe to re-run any time.

./scripts/install-linux.sh

Prefer doing it by hand instead?

cargo build --release
cargo test --release
3

Run it — as root, for full attribution

GasLight's Linux file-write attribution uses fanotify, which needs CAP_SYS_ADMIN. It runs fine without root too — just with reduced attribution, the same tradeoff Windows always has.

Run asFile-write attribution
sudo ./target/release/gaslight-agentReal PID per write — fanotify active
./target/release/gaslight-agentWorks fine; writes bucketed under a generic "SYSTEM" process
Not a crash either way. The agent probes fanotify availability at startup and logs which mode it's running in — check for [fanotify] PID-attributed write monitor active vs. [fanotify] not available in the console.

4

Optional: enable real enforcement

By default, "blocking" a process only logs the intent — same as every other platform. On Linux, you can make it real: gaslight.toml's [enforcement] section can turn on fanotify-permission-based write blocking, entirely in user space, no kernel module.

Read this before flipping it on. Enforcement pauses every file open() under your watched paths until GasLight responds — a bug means that open() call hangs forever, not just fails to protect. It's fail-open by design (only PIDs the behavioral engine explicitly flags get denied) and only watches your configured paths, not the whole filesystem, but it's still a fundamentally different risk than everything else in this project. Full reasoning in src/enforcement/fanotify_guard.rs's module comment — read it first. 
# gaslight.toml
[enforcement]
enabled = true

Needs root either way. Check the log for [enforcement] fanotify permission enforcement ACTIVE to confirm it actually turned on (vs. silently falling back to log-only if the process wasn't root).

6

Confirm it's actually working

A watched/ folder is created on first run, with real decoy files deployed into it automatically — check the log for [deception] deployed N decoy file(s). Then:

# touch a real generated decoy directly (check the log for its exact name)
echo "test" >> watched/Finance/Payroll_2026_Q1.xlsx

# or simulate generic ransomware-like write behavior:
for i in $(seq 1 50); do head -c 4096 /dev/urandom > "watched/f$i.tmp"; mv "watched/f$i.tmp" "watched/f$i.locked"; done
  • Dashboard's Honey File Monitor panel shows the interaction
  • Process table shows a rising risk score with a real reasons breakdown
  • If run as root, the process name is the real one — not "SYSTEM (unattributed)"
  • If enforcement is enabled, a flagged process's further file opens under watched/ actually fail — not just get logged
